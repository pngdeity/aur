# .SRCINFO Version Control Policy

**Date:** 2026-05-15
**Status:** Adopted
**Audience:** Maintainers, CI/CD pipelines, automated agents

---

## Background

`.SRCINFO` is a static, machine-parseable metadata file generated from a `PKGBUILD` by `makepkg --printsrcinfo`. Per the Arch Wiki and `SRCINFO(5)`, it is the canonical format consumed by AUR helpers (`yay`, `paru`, etc.) and the AUR web interface for dependency resolution, conflict detection, and package discovery without executing `PKGBUILD` code.

In this repository, `.SRCINFO` files currently exist in 6 of 8 package directories. The AGENTS.md mandatory verification workflow (§3, step 3) requires regeneration after every `PKGBUILD` change. The `build.yml` CI pipeline runs `scripts/check-metadata.sh` — a diff-based validator that compares the committed `.SRCINFO` against a freshly generated copy and fails if they diverge. The `discovery.yml` pipeline commits `.SRCINFO` alongside automated `PKGBUILD` updates.

Meanwhile, `scripts/aur-deploy.sh` independently generates `.SRCINFO` from a *processed* `PKGBUILD` (after inlining `source` directives, stripping repo-local variables, and removing `# PREREVIEW:` markers) and pushes that version to `aur.archlinux.org`. These two `.SRCINFO` files — the committed source-repo copy and the AUR-deployed copy — are not the same file. The deployed copy is a transformed derivative.

This document evaluates whether `.SRCINFO` files should be checked into this repository's version control, given this architecture.

---

## Analysis

| Criterion | Check In (PRO) | Don't Check In (CON) |
|---|---|---|
| **Functional consumer** | `check-metadata.sh` uses it for diff-based validation | No downstream consumer uses the committed copy — AUR helpers read from AUR git, not this repo |
| **AUR deployment** | Already generated by `aur-deploy.sh` as a dependency | `aur-deploy.sh` generates its own `.SRCINFO` from the processed PKGBUILD — the committed copy is irrelevant to deployment |
| **CI validation** | Provides a snapshot to diff against; catches accidental PKGBUILD metadata breakage before commit | Same validation achievable via `makepkg --printsrcinfo > /dev/null` (syntactic check) without a committed baseline |
| **Merge conflicts** | Rare in practice (concurrent edits to the same package are infrequent) | When they occur, `.SRCINFO` is a large, mechanically-generated file that produces noisy conflicts requiring blind regeneration |
| **Maintenance burden** | Forces discipline: desyncs surface as CI failures, prompting the maintainer to regenerate | Desync is a recurring chore that wastes human and agent time — the file is trivially regenerable and carries no unique information |
| **Commit noise** | Documents expected metadata state at each commit, serving as an audit trail | Adds ~20–50 lines of boilerplate to every PKGBUILD-touching commit; pollutes `git log` and `git blame` |
| **Repository integrity** | A commit's `.SRCINFO` is always consistent with its `PKGBUILD` (enforced by CI) | PKGBUILD changes are the source of truth; `.SRCINFO` is a projection — storing both is redundant |
| **Arch Linux convention** | The AUR git repositories (hosting individual packages) mandate `.SRCINFO` via `aurweb` server-side enforcement | This is not an AUR git repository — it's a source/monorepo that *produces* AUR-compatible output. The AUR git repos will always have `.SRCINFO`; this repo does not need to |

### Key Architectural Insight

The committed `.SRCINFO` in this repository has exactly **one** functional consumer: `scripts/check-metadata.sh`, which diffs it against a fresh generation. It is not consumed by:

- **AUR helpers** — they read `.SRCINFO` from `aur.archlinux.org/<pkg>.git`, not from this repo
- **`aur-deploy.sh`** — it generates its own `.SRCINFO` from the processed PKGBUILD
- **`makepkg`** — it reads the `PKGBUILD` directly; `.SRCINFO` is a makepkg *output*, not an input
- **`namcap`** — it operates on the `PKGBUILD` or built package
- **Any build step** — `arch-builder.sh`, `pkgctl build`, and `makechrootpkg` all consume `PKGBUILD` exclusively

In every case, the `PKGBUILD` is the authoritative source. `.SRCINFO` is a lossy, derived view of it.

---

## Recommendation

**Do NOT check `.SRCINFO` files into version control.**

The committed `.SRCINFO` files provide zero functional value to any consumer. They are derived artifacts — equivalent to build output — that serve only as the target of a diff-based validation check. That validation can be replaced with a syntactic pass (`makepkg --printsrcinfo > /dev/null`) without losing coverage, since a `PKGBUILD` that fails `makepkg --printsrcinfo` is already a build-breaking error and a `PKGBUILD` that succeeds it is syntactically valid — the desync risk is that metadata drifted, but metadata drift between a valid `PKGBUILD` and its `.SRCINFO` only matters at AUR-deploy time, and `aur-deploy.sh` generates a fresh `.SRCINFO` at that exact moment.

### Rationale

1. **No functional consumer.** If no tool reads the committed `.SRCINFO`, it is dead weight. The one tool that does (`check-metadata.sh`) can be redesigned.
2. **Duplication of truth.** Every field in `.SRCINFO` is already present in `PKGBUILD`. Maintaining both is a violation of the Single Source of Truth principle.
3. **Self-inflicted chore.** The desync "problem" is an artifact of a process that requires manual regeneration of a derived file. Eliminating the file eliminates the problem.
4. **AUR deployment is unaffected.** `aur-deploy.sh` generates `.SRCINFO` on-the-fly from the processed PKGBUILD. The AUR git repositories will continue to have valid `.SRCINFO` files.
5. **Precedent in software engineering.** Generated artifacts (compiled binaries, minified assets, dependency lockfiles from resolved graphs) are widely excluded from version control in monorepo patterns. `.SRCINFO` is no different.

## Implementation

### Phase 1: Remove committed `.SRCINFO` files

```bash
# Remove from git tracking (keep local copies for now)
git rm --cached packages/*/.SRCINFO
```

Add to `.gitignore`:
```gitignore
# Generated metadata — regenerated by makepkg --printsrcinfo
packages/*/.SRCINFO
```

### Phase 2: Replace diff-based validation with syntactic validation

Replace `scripts/check-metadata.sh` (diff-based) with a lighter check:

```bash
#!/usr/bin/env bash
# scripts/check-metadata.sh (revised)
# Validates that PKGBUILD can produce valid .SRCINFO.
set -euo pipefail

PKG_DIR=$1
cd "$PKG_DIR"

# Syntactic validation: PKGBUILD must produce parseable metadata
makepkg --printsrcinfo > /dev/null
echo "  -> PKGBUILD produces valid .SRCINFO metadata."
```

This tests what actually matters: can the PKGBUILD generate valid AUR metadata? The answer must be "yes" for AUR deployment to succeed. A diff against a stale committed copy provides no additional safety.

### Phase 3: Update agent workflows

- **`AGENTS.md` §3 step 3**: Change from `makepkg --printsrcinfo > .SRCINFO` to a validation-only check
- **`pkg-update` skill**: Remove `.SRCINFO` commit step; `sync-package.sh` regenerates for local convenience but git ignores it
- **`pkg-bootstrap` skill**: Same
- **`pkg-patch-recovery` skill**: Same
- **`discovery.yml`**: Remove `.SRCINFO` from the `git add` path (it's already ignored by `.gitignore`)

### Phase 4: Keep local convenience generation

`sync-package.sh` may continue to run `makepkg --printsrcinfo > .SRCINFO` for local developer convenience (e.g., `namcap`-like tooling, manual inspection). The `.gitignore` rule ensures it never reaches version control again. This is zero-cost to retain.

### Exceptions

None. This policy applies uniformly to all packages in this repository. The AUR git repositories — which are the canonical `.SRCINFO` hosts — are managed by `aur-deploy.sh` and are outside the scope of this policy.

## Appendix: Rejected Alternatives

### Git attributes smudge/clean filters
**Rejected.** Over-engineering. A filter would auto-generate `.SRCINFO` on checkout and strip it on commit. This hides the problem rather than solving it and introduces tooling dependencies for basic git operations.

### Submodule the AUR git repos
**Rejected.** This repo is the source of truth for upstream code; the AUR repos are downstream deployment targets. Submoduling would invert the dependency DAG and create circular tooling requirements.

### Keep status quo
**Rejected.** The `.SRCINFO` desync has required manual regeneration across multiple agent sessions and remains a recurring source of CI failures. The cost of maintaining the current approach exceeds its (zero) functional benefit.
