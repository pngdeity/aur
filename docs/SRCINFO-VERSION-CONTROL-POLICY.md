# .SRCINFO Version Control Policy

**Date:** 2026-05-15 **Status:** Adopted **Audience:** Maintainers, CI/CD
pipelines, automated agents

---

## Background

`.SRCINFO` is a static, machine-parseable metadata file generated from a
`PKGBUILD` by `makepkg --printsrcinfo`. Per the Arch Wiki and `SRCINFO(5)`, it
is the canonical format consumed by AUR helpers (`yay`, `paru`, etc.) and the
AUR web interface for dependency resolution, conflict detection, and package
discovery without executing `PKGBUILD` code.

In this repository, `.SRCINFO` files were committed in early package
directories. The AGENTS.md mandatory verification workflow (§3, step 3) requires
a syntactic `makepkg --printsrcinfo > /dev/null` metadata pass (no committed
`.SRCINFO` baseline). The `build.yml` CI pipeline runs Pkl schema validation and
`check-pkgdesc-consistency.sh` — no diff-based `.SRCINFO` comparison.
The `discovery.yml` pipeline opens a PR for automated
`PKGBUILD` updates without committing `.SRCINFO`.

Meanwhile, `scripts/aur-deploy.sh` independently generates `.SRCINFO` from a
_processed_ `PKGBUILD` (after inlining `source` directives, stripping repo-local
variables, and removing `# PREREVIEW:` markers) and pushes that version to
`aur.archlinux.org`. These two `.SRCINFO` files — the committed source-repo copy
and the AUR-deployed copy — are not the same file. The deployed copy is a
transformed derivative.

This document evaluates whether `.SRCINFO` files should be checked into this
repository's version control, given this architecture.

## Analysis

| Criterion                 | Check In (PRO)                                                                                                 | Don't Check In (CON)                                                                                                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Functional consumer**   | (removed — `check-metadata.sh` was the sole consumer and has been deleted)                                                        | No downstream consumer uses the committed copy — AUR helpers read from AUR git, not this repo                                                                               |
| **AUR deployment**        | Already generated by `aur-deploy.sh` as a dependency                                                           | `aur-deploy.sh` generates its own `.SRCINFO` from the processed PKGBUILD — the committed copy is irrelevant to deployment                                                   |
| **CI validation**         | Provides a snapshot to diff against; catches accidental PKGBUILD metadata breakage before commit               | Same validation achievable via `makepkg --printsrcinfo > /dev/null` (syntactic check) without a committed baseline                                                          |
| **Merge conflicts**       | Rare in practice (concurrent edits to the same package are infrequent)                                         | When they occur, `.SRCINFO` is a large, mechanically-generated file that produces noisy conflicts requiring blind regeneration                                              |
| **Maintenance burden**    | Forces discipline: desyncs surface as CI failures, prompting the maintainer to regenerate                      | Desync is a recurring chore that wastes human and agent time — the file is trivially regenerable and carries no unique information                                          |
| **Commit noise**          | Documents expected metadata state at each commit, serving as an audit trail                                    | Adds ~20–50 lines of boilerplate to every PKGBUILD-touching commit; pollutes `git log` and `git blame`                                                                      |
| **Repository integrity**  | A commit's `.SRCINFO` is always consistent with its `PKGBUILD` (enforced by CI)                                | PKGBUILD changes are the source of truth; `.SRCINFO` is a projection — storing both is redundant                                                                            |
| **Arch Linux convention** | The AUR git repositories (hosting individual packages) mandate `.SRCINFO` via `aurweb` server-side enforcement | This is not an AUR git repository — it's a source/monorepo that _produces_ AUR-compatible output. The AUR git repos will always have `.SRCINFO`; this repo does not need to |

### Key Architectural Insight

The committed `.SRCINFO` in this repository had exactly **one** historical
consumer: `scripts/check-metadata.sh`, which performed a diff-based comparison.
It is not consumed by:

- **AUR helpers** — they read `.SRCINFO` from `aur.archlinux.org/<pkg>.git`, not
  from this repo
- **`aur-deploy.sh`** — it generates its own `.SRCINFO` from the processed
  PKGBUILD
- **`makepkg`** — it reads the `PKGBUILD` directly; `.SRCINFO` is a makepkg
  _output_, not an input
- **`namcap`** — it operates on the `PKGBUILD` or built package
- **Any build step** — `arch-builder.sh`, `pkgctl build`, and `makechrootpkg`
  all consume `PKGBUILD` exclusively

In every case, the `PKGBUILD` is the authoritative source. `.SRCINFO` is a
lossy, derived view of it.

---

## Recommendation

**Do NOT check `.SRCINFO` files into version control.**

The committed `.SRCINFO` files provide zero functional value to any consumer.
They are derived artifacts — equivalent to build output — that serve only as the
target of a diff-based validation check. That validation can be replaced with a
syntactic pass (`makepkg --printsrcinfo > /dev/null`) without losing coverage,
since a `PKGBUILD` that fails `makepkg --printsrcinfo` is already a
build-breaking error and a `PKGBUILD` that succeeds it is syntactically valid —
the desync risk is that metadata drifted, but metadata drift between a valid
`PKGBUILD` and its `.SRCINFO` only matters at AUR-deploy time, and
`aur-deploy.sh` generates a fresh `.SRCINFO` at that exact moment.

### Rationale

1. **No functional consumer.** If no tool reads the committed `.SRCINFO`, it is
   dead weight. The one tool that did (`check-metadata.sh`) has been removed.
2. **Duplication of truth.** Every field in `.SRCINFO` is already present in
   `PKGBUILD`. Maintaining both is a violation of the Single Source of Truth
   principle.
3. **Self-inflicted chore.** The desync "problem" is an artifact of a process
   that requires manual regeneration of a derived file. Eliminating the file
   eliminates the problem.
4. **AUR deployment is unaffected.** `aur-deploy.sh` generates `.SRCINFO`
   on-the-fly from the processed PKGBUILD. The AUR git repositories will
   continue to have valid `.SRCINFO` files.
5. **Precedent in software engineering.** Generated artifacts (compiled
   binaries, minified assets, dependency lockfiles from resolved graphs) are
   widely excluded from version control in monorepo patterns. `.SRCINFO` is no
   different.

## Implementation

### Phase 1: Remove committed `.SRCINFO` files — **Completed**

```bash
# Already executed — no .SRCINFO files remain tracked
# git rm --cached packages/*/.SRCINFO
```

`.gitignore` entry applied (`packages/*/.SRCINFO` at line 46).

### Phase 2: Replace diff-based validation with syntactic validation — **Completed 2026-05-27**

`scripts/check-metadata.sh` was retired and removed — Pkl schema validation has
fully superseded the diff-based `.SRCINFO` comparison.

This tests what actually matters: can the PKGBUILD generate valid AUR metadata?
The answer must be "yes" for AUR deployment to succeed. A diff against a stale
committed copy provides no additional safety.

### Phase 3: Update agent workflows — **Completed 2026-05-27**

- **`AGENTS.md` §3 step 3**: Changed to `makepkg --printsrcinfo > /dev/null`
  with note that `.SRCINFO` is not version-controlled.
- **`pkg-update` skill**: Removed `.SRCINFO` from commit step; metadata step
  changed to validation-only.
- **`pkg-bootstrap` skill**: Changed to validation-only (`> /dev/null`).
- **`pkg-patch-recovery` skill**: Changed to validation-only (`> /dev/null`).
- **`discovery.yml`**: Safe — `git add packages/` excludes `.SRCINFO` via
  `.gitignore`.

### Phase 4: Remove `.SRCINFO` from sync-package.sh — **Completed 2026-06-01**

`sync-package.sh` no longer generates `.SRCINFO` at all. The `.SRCINFO` metadata
file is exclusively a deployment artifact, generated on-the-fly by
`scripts/aur-deploy.sh` during the AUR push step. This ensures a single point of
generation — at the deployment boundary, from the processed (inlined, stripped)
PKGBUILD — with zero risk of committed `.SRCINFO` desync.

### Exceptions

None. This policy applies uniformly to all packages in this repository. The AUR
git repositories — which are the canonical `.SRCINFO` hosts — are managed by
`aur-deploy.sh` and are outside the scope of this policy.

## Appendix: Rejected Alternatives

### Git attributes smudge/clean filters

**Rejected.** Over-engineering. A filter would auto-generate `.SRCINFO` on
checkout and strip it on commit. This hides the problem rather than solving it
and introduces tooling dependencies for basic git operations.

### Submodule the AUR git repos

**Rejected.** This repo is the source of truth for upstream code; the AUR repos
are downstream deployment targets. Submoduling would invert the dependency DAG
and create circular tooling requirements.

### Keep status quo

**Rejected.** The `.SRCINFO` desync has required manual regeneration across
multiple agent sessions and remains a recurring source of CI failures. The cost
of maintaining the current approach exceeds its (zero) functional benefit.
